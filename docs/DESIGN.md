## 一、数值可信化

### 问题的本质

市面上的 AI 营养助手都是「LLM 自由回答」。这带来一个致命缺陷：

> **AI 给健康建议最严重的问题不是答不上，而是编数字。**

BMR 算成 1720 还是 1820，差 100 千卡就是一天的热量差。体重 10 公斤的
用户按错误 BMR 吃一个月，会造成 3 万千卡的累积偏差。

### 最初的误区

第一版我把护栏当万能药：检测到裸数字就替换成「（数据待核实）」。

结果**满屏都是「数据待核实」**，比编数字更糟——用户什么答案都拿不到。

实测诊断：21 种问法里有 **9 种泄漏**，而且不是同一个原因。

### 真正的规律

复盘后发现一条关键规律：

> **凡是问题本身需要数字、而系统没有对应工具的，模型就只能编。**

「模型编数字」几乎总是**系统能力缺失的信号**，不是模型的错。

于是问题从「怎么拦住模型编数字」变成「**怎么让模型有数字可用**」。

### 最终方案：可信算术

不是禁止模型算，而是**允许它算，但只能用数据库给的数字算**。

```python
{{calc: met_1 * weight_kg_1 * 30 / 60}}
       └── 系统真实执行这个算式并填入结果
```

**为什么这能根治：**

| 环节 | 是否可能幻觉 |
|---|---|
| 模型**运算** | ❌ 运算确定，不产生幻觉 |
| 模型的**输入** | ❌ 全部来自数据库 |

幻觉只可能来自输入，而输入全部可追溯 —— 于是「算」这一步没有幻觉风险。

**关键突破：不需要穷举意图。** 只要 MET 和体重两个原料给出去，
「步行消耗多少」「慢跑大吗」「走路一小时能瘦多少」全都能算。

补充的原料兜底在 `app/services/exercise_ref.py`：涉及运动/消耗的问题
统一补 12 种常见运动 MET + 用户体重。

### 安全边界

算术引擎用 **AST 白名单求值，不是 eval**。

```python
# 只允许这四类节点
Constant / Name / BinOp / UnaryOp
```

23 项攻击全部拦截：

```
❌ __import__('os').system('ls')    ❌ met.__class__
❌ print('hi')                ❌ [1,2,3][0]
❌ met ** 1000                       ❌ eval('1+1')
❌ 除以零 / 未知变量 / lambda / f字符串 / 赋值 / 注入分号
```

变量必须来自数据库槽位；除零有阈值保护；结果超 1e9 拒绝。
**模型能做的运算严格限定在加减乘除，无法执行任意代码。**

### 最终效果

```
python scripts/verify_no_hallucination.py
泄漏 0/21
```

21 种问法连续三轮零泄漏，含「正常人一天睡几小时」这类
**不该拦的反例**（验证没有过度拦截）。

## 二、架构取舍

### 刻意不用 LangGraph

项目装了 LangGraph，但**对话编排手写状态机**。

```python
# app/graph/workflow.py
"""这是编排的主入口。为了可控性与可调试性，这里手写了节点转移
而不是用 StateGraph.compile() —— 转移逻辑就三条路径，
用框架反而绕。真正的多轮能力由 prev_state 的状态继承提供。"""
```

**理由**：意图识别 → 工具执行 → 分支 → 生成，转移逻辑只有三条。
引入状态机框架增加的心智负担大于收益。真正的多轮能力靠
`prev_state` 的状态继承，而不是靠图。

多轮追问（做菜要问油量、名字歧义要问选哪个）用框架确实更清晰，
但那部分逻辑本身只有两个分支，用框架反而绕。

### 意图识别：规则优先，LLM 兜底

13 类意图中，**能靠正则与量词规则命中的绝不调 LLM**：

```python
if any(w in text for w in ("体重", "身高")):
    ...
if any(w in text for w in ("吃完", "吃", "喝")) and any(w in text for w in ("多久", "消耗")):
    ...
```

规则层的价值不只是快——它是**确定性**的，不会今天判 A 明天判 B。
只有规则拿不准时才交给 LLM（结果进有界 LRU 缓存，重复问题不再调 LLM）。

### 数值一律整句绑定

工具返回的不是散装数字，而是把名称与数值绑成一个值：

```python
{
    "name": "跳绳",
    "met": 12.3,
    "kcal_per_hour": 1150.2,
    "line": "跳绳（MET 12.3，每小时约 1150.2 千卡）",
}
```

**为什么**：如果只给 `item1_kcal: 25.0`，模型看不到它属于哪个食物，
只能写成「食物1」，甚至可能把跳绳的 MET 写到跑步头上。
整句绑定从数据结构上杜绝张冠李戴。

这是踩过坑之后加的——早期的食物推荐只返回
`item1_kcal` / `item1_protein`，用户看到的就是「食物1、食物2」。

### 意图优先于校验

```
run_chat()：识别意图 → 取数 → 分支 → 生成 → 渲染校验
                              ↑
                        纯计算，不碰 LLM
```

工具层是纯函数式计算，可单测、可复现。LLM 只负责「把已确定的数字组织成自然语言」。
这样即使 LLM 不可用（断网、额度耗尽），系统仍能返回数据库真值。

## 三、踩坑记录

### 1. 数值幻觉：以为是护栏问题，其实是能力缺失

**现象**：满屏「数据待核实」。

**误诊**：以为是护栏阈值太严，放宽了白名单。
→ 假数字混进来了，更糟。

**真相**：9/21 的泄漏对应 9 个能力缺口（缺时长、缺量词换算、缺多食物查询…）。

**教训**：护栏是最后一道防线，不是主要手段。
**「模型编数字」是信号，说明系统缺东西了。**

### 2. 半角括号：用户猜对了现象，但猜错了原因

用户报「炸鸡查不到，可能多了个括号」。

括号确实有问题（半角 `炸鸡(去骨)` 命中不了库里的全角 `炸鸡（去骨）`），
但**不是主因**。真因是：

```python
# 抽取词表只收 FoodItem.name，没收 base_name
for n in db.execute(select(FoodItem.name)).scalars().all():
    names.add(n)
    # ← 库里的「炸鸡」只是 base_name，正式名是「炸鸡（去骨）」
```

所以用户问「200克炸鸡」抽不出食物名 → 意图退到 KNOWLEDGE_QA →
模型自由发挥说「库里没有炸鸡」。**数据明明在库里。**

**教训**：用户对现象的直觉往往对，但根因需要用数据验证。

### 3. 假流式：接口名叫 stream，内部是一次性返回

```python
@router.post("/chat/stream")          # 名字叫流式
def chat_stream(req, db):
    result = run_chat(db, req.message)   # 等完整答案生成完
    yield emit("token", {"content": result.answer})  # 一次性推
```

`client.chat_stream()` 早就写好了，**从没被对话链路调用过**。
实测首token 延迟 19.37 秒 —— 用户全程干等。

**教训**：**名字叫流式不等于流式**。要实测首token 延迟，不能信函数名。

### 4. `use_llm=False` 是假的

做流式改造时，我用 `run_chat(use_llm=False)` 做「先取数再生成」的预取。
但这个开关**只传给了意图识别**，`generate_answer` 照样执行：

```python
intent_result = classify_intent(user_input, use_llm=use_llm)  # 只这里用
# generate_answer(state)  ← 完全无视 use_llm
```

预取阶段白等 14.62 秒，整个流式改造方案作废。

**教训**：**开关要验证真的生效**。名字叫 `use_llm=False`，
不代表它真的不调 LLM。

### 5. 只加新路径，不删旧路径

改完流式后忘了删改造前的旧代码，两段逻辑并存：

```python
# 新路径：逐 token 推
yield emit("token", {"content": visible})
# 旧路径残留：又整体推一遍
yield emit("token", {"content": result.answer})   # ← 内容翻倍
```

用户反馈「答完就崩」。

**教训**：**改造时「删掉旧路径」和「加新路径」同样重要**。
只加不删 = 重复执行。

### 6. 整页白屏：不是内容太多，是字段缺失

用户报「推荐食物答完就崩」，第一次我诊断成「内容重复撑爆页面」。
第二次给截图才看清：**整个页面全空了，连输入框都没了**。

真因：

```python
# 后端
citations.append({"type": "recommend", "items": [...]})   # 没有 name
# 前端
{c.name.slice(0, 40)}    # undefined.slice() → TypeError
```

React 里任何渲染期异常都会**卸载整棵组件树**，不是只崩出错的那个组件。

而类型定义写的是 `name: string`（必填）—— **类型在骗人**，
所以没人发现后端不返回这个字段。

**教训**：
- 「白屏」和「内容变长」是两类问题，看到截图才有方向
- TypeScript 类型只保证编译期，不保证运行时数据真的符合
- 已加 `ErrorBoundary`：任何渲染异常都降级为提示，**永不再白屏**

### 7. 流式与占位符冲突

流式时 token 碎片化到达：`{{kca` + `l_1` + `}}`。
逐 token 直推会让用户看到占位符闪烁再消失——**比一次性显示更糟**。

解法是 `app/llm/stream_render.py`：缓冲到 `}}` 才判定为完整占位符，
立刻查表替换后推送。同时要处理普通大括号（`{a, b}` 不能被误吞）
和缓冲上限（防模型输出大量 `{` 导致卡住）。

### 8. 护栏白名单漏扫

```python
for k in filled:          # ← 只扫「模型引用过的槽位」
    if isinstance(sl.value, str): ...
```

流式路径下占位符已被提前替换，文本里没有 `{{}}` → `filled` 是空 →
白名单为空 → 数据库返回的 96 / 78.2 / 10.5 全被判成幻觉。

**用户看到「检测到 6 个未经数据库核实的数字」，与事实完全相反。**

改成扫描全部字符串槽位。教训：白名单的数据来源要覆盖所有路径。

## 四、性能优化

### 先量再改

优化前先测出时间分布：

```
意图识别  0.04s（规则）/ 1.5s（LLM）
工具取数  0.01s（本地）
LLM 生成  13.60s     ← 瓶颈全在这
```

四个瓶颈，按收益排序：

### ① 关闭深度思考（收益最大）

qwen3 系列默认开启 `enable_thinking`，会先花大量 token 推理。

| enable_thinking | 耗时 | 输出 |
|---|---|---|
| True | 14.86s | 546 tok |
| **False** | **5.35s** | 255 tok |

本项目是「查库 + 引用数字」，不需要复杂推理。**快 2.8 倍。**

可通过环境变量切换：`LLM_ENABLE_THINKING=true` 恢复。

### ② 接通真流式

首token 延迟 **19.37s → 0.62s**（裸模型测试）。

改造中走过两条弯路，都推翻重做：

1. **「流式重放」**：先跑一次拿答案，再调第二次流式重播。
   多了整整一次 LLM 调用，**反而更慢**。
2. **`on_token` 回调**：同步生成器里回调**无法 yield**，
   只能收集后一次性推，又失去流式意义。

最终改为在生成器里直接迭代 `chat_stream` 并 `yield`。

### ③ 修复 use_llm 失效

预取阶段 14.62s → 1.06s（详见踩坑 4）。

### ④ 意图缓存

规则匹配不到时才走 LLM，这条路径要 5~16 秒。
加有界 LRU（`OrderedDict`，上限 500）后：**1.75s → 0.00s**。

### 最终效果（端到端 SSE 实测）

| 场景 | 意图 | 首token | 总耗时 |
|---|---|---|---|
| 知识问答（冷启动） | 1.15s | 2.36s | 18.59s |
| 知识问答（同题） | 0.45s | 1.79s | 13.76s |
| 查热量（规则命中） | 0.05s | **0.88s** | 1.19s |

**首token 19.37s → 0.88s**，用户能看到文字逐字出现而不是干等。

## 五、测试策略

### 326 个用例的分布

| 测试类 | 数量 | 覆盖内容 |
|---|---|---|
| `TestCalculator` | 6 | 算术引擎正确性 + **23 项攻击拦截** |
| `TestCalcRendering` | 5 | `{{calc}}` 在渲染管线生效 |
| `TestPromptStructure` | — | 数值契约注入 |
| `TestClientStatus` | — | 配置项（不写死具体值） |
| 意图回归 | ~20 | **每个真实 bug 一个用例** |
| 公式与边界 | — | BMI/BMR 各标准、空值、异常输入 |
| 服务层 | — | 食物查询、换算、份量换算 |

### 核心原则：测试要记录「为什么存在」

```python
def test_rejects_code_execution(self):
    """绝不能执行任意代码 —— 这是安全底线。"""

def test_never_leaks_placeholder(self):
    """任何碎片化方式都不该把 {{ 露给用户。"""

def test_portion_not_swallowed_in_name(self):
    """剥量词不能把食物名一起剥掉（「碗米饭」不是纯量词）。"""
```

这些注释是**思考过程的证据**。测试不只是防回归，
它记录了「这里曾经出过什么问题」。

### 泄漏检测脚本

`scripts/verify_no_hallucination.py` 覆盖 21 种问法，
含**不该拦的反例**（验证没有过度拦截）：

```bash
$ python scripts/verify_no_hallucination.py
✅ 步行能消耗多少热量    ✅ 走路消耗多少
✅ 慢跑消耗大吗          ✅ 快走30分钟消耗多少
✅ 正常人一天睡几小时    ← 反例：不该拦的也没拦
泄漏 0/21
```

### 踩过的坑：测试覆盖的是「我以为的调用方式」

`StreamRenderer` 我写成：

```python
self._slots = build_slots(slots) if not hasattr(slots, "__iter__") else slots
```

判断反了。单元测试传的是已构建的 `Slot` 对象（走对了分支），
但生产调用传的是原始 `dict` 列表（走错分支）→ SSE 路径直接崩。

浏览器验收（`verify_ui.mjs`）才抓到。

**教训**：单测要覆盖**真实的调用方式**，不只是逻辑本身。

## 六、数据一致性

### 改身高会重算全部历史 BMI

这不是常见做法，但它很关键：

```sql
-- 体重没变、身高变了 → 全部历史 BMI 重算
UPDATE weight_logs SET bmi = ? / (?) * 10000
```

否则会出现「今天 BMI 24，去年 BMI 28，但身高从没变过」的矛盾曲线。

### BMI 标准锁定在每条记录上

每条体重记录都存了 `bmi_standard`（中国标准 / WHO 标准）。
中国标准 overweight 阈值是 28，WHO 是 25——

如果不锁定标准，用户中途切换后整条曲线会「变色」，
看起来像数据错了，实际只是标准变了。

## 七、已知限制

| 限制 | 说明 |
|---|---|
| 单用户 | 无登录与多用户隔离，演示模式 |
| 无 Embedding 缓存持久化 | `embed_cache.json` 不入库，首次构建知识库需调嵌入 API |
| 意图路由边界模糊 | 如「苹果有什么营养」既像查库又像知识问答，走前者 |
| 数据集不完整 | 常见水果（苹果、香蕉）部分条目缺失，USDA 数据以美式食物为主 |

这些限制都是**已知且有意保留**的——补全它们需要更大的数据集，
对展示核心技术点没有增量价值。
