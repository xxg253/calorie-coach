# P2 · React 前端

## 一、启动（两个服务都要）

```bash
# 终端 1：后端（项目根目录）
.venv/Scripts/python.exe -m uvicorn app.main:app --port 8000

# 终端 2：前端（frontend 目录）
cd frontend
npm install          # 首次
npm run dev          # → http://127.0.0.1:5173
```

后端没启动时前端不会白屏，顶部会显示「后端未连接」并给出启动命令。

## 二、技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 框架 | React 18 + TypeScript + Vite 8 | Vite 8 已切到 rolldown，构建快 |
| UI | Ant Design 6 | 注意 v6 的 API 变更，见下方踩坑 |
| 图表 | ECharts 5 + echarts-for-react | 体重趋势 / 收支对比 |
| 数据 | TanStack Query v5 | 自动缓存、失效、加载态 |
| 路由 | React Router 6 | 看板 / 记录 / 对话 三页 |
| 网络 | axios + 原生 fetch(SSE) | SSE 必须用 fetch，EventSource 不支持 POST |

**为什么不用 Ant Design Pro / 现成模板**：这个项目的界面重点是把「数值从哪来」讲清楚
（配料明细、计算过程可展开、SQL 可展开、数据库返回值可展开），
现成模板反而要花更多时间改掉它自带的东西。

## 三、三个页面的设计意图

### 看板页 `/`

| 设计 | 为什么 |
|---|---|
| BMR / TDEE / 额外运动 **三个数字同屏** | 用户最大的认知误区是把基础代谢当日消耗。UI 上分开显示比任何文字解释都有效 |
| 体重折线**必须**叠加 7 日移动平均 | 日间 ±1.5kg 波动属正常。只画原始值，用户看到噪音就放弃了 |
| 推荐区**可展开查看实际 SQL** | 证明「低热量高蛋白」是 `kcal<=80 AND protein>=5` 查出来的，不是向量猜的。这是面试可讲的点 |
| 热量缺口用箭头 + 红绿区分 | 中国用户习惯：缺口为正是好事，用绿色 |

### 记录页 `/record`

核心是**两阶段确认**（红线三）与**追问流程**：

```
输入「西红柿炒鸡蛋」→ 点计算
  ↓ 后端判定信息不足（need_clarify）
  ↓ 前端弹出做法/油量选择
选「炒」+「清淡」
  ↓ 再次计算 → 信息充分
  ↓ POST /api/intake/preview（不落库）
  ↓ 弹确认框，显示配料明细与最终热量
点「确认记录」→ POST /api/intake（落库）
```

**配料明细表**让用户看得见热量是怎么算出来的：西红柿 100g×20 + 鸡蛋 60g×85.8
+ 植物油 15g×134.8 = 254.1 千卡，然后 ×1.25 炒菜倍率。透明度比精确度更能建立信任。

**歧义弹窗**（红线四）：命中多个同名记录时弹出单选，
明确写「系统不会替你猜，也不会取平均值」。

### 对话页 `/chat`

| 功能 | 实现 |
|---|---|
| SSE 流式 | `fetch` + `ReadableStream` 手工解析 SSE，事件为 `{type, data}` 嵌套 |
| 多轮追问 | 追问选项渲染成可点击的标签，点一下就回答，不用打字 |
| 数据来源 | 折叠面板展示引用的切片 |
| **数据库返回值** | 折叠展示本次工具返回的原始 JSON —— 一眼看出 232 不是模型算的 |
| 数值校验警告 | 后端检测到模型输出了未核实数字时，以黄色条提示 |

## 四、自己写而不交给库的部分

| 模块 | 原因 |
|---|---|
| SSE 解析 | EventSource 只支持 GET，对话必须 POST，只能用 fetch 手写 |
| 槽位与数据来源展示 | 这是本项目的核心可信度机制，用现成组件表达不出来 |
| 两阶段确认的状态机 | 涉及 preview/create/歧义/追问四条分支，封装起来反而更绕 |

## 五、验收方式

三层验证，缺一不可：

```bash
# 1. 类型（编译期）
npm run typecheck

# 2. 构建（打包期）
npm run build

# 3. 真浏览器（运行期）—— 21 项端到端检查 + 三张截图
node scripts/verify_ui.mjs
```

**为什么必须真浏览器**：类型检查和构建通过只证明「能编译」，
不证明「能跑」。P2 期间靠这一步抓到了四个只有运行期才暴露的问题，
其中两个是布局类 bug，看代码完全正常。

## 六、P2 期间抓到的问题

| # | 问题 | 原因 | 怎么发现的 |
|---|---|---|---|
| 1 | **确认弹窗永远不出现（死循环）** | 前端调 `calcRecipe` 时没把用户已选的烹饪方式/油量传过去，后端每次都判定「信息不足」反复返回追问 | 浏览器验收卡在第 13 项，抓网络请求才定位 |
| 2 | **整页布局塌陷** | 外层 `<Space>` 默认横向排列，把所有 `Row/Col` 挤成一行，卡片被压成窄条、图表被压扁 | **看截图** —— 断言全过但视觉是坏的 |
| 3 | **蒸菜仍追问用油量** | 后端 `recipe_need_oil_level` 只看菜谱默认做法，不看用户实际选的烹饪方式 | 验收日志里出现「蒸（清淡油量）」这种矛盾组合 |
| 4 | **构建直接失败** | Vite 8 用 rolldown，`manualChunks` 对象形式不再支持，必须用函数 | `npm run build` 报错 |
| 5 | 控制台 4 类废弃告警 | antd v6 改了 API：`valueStyle→styles.content`、`message→title`、`addonAfter→Space.Compact`、`bordered→variant` | 浏览器控制台捕获 |

**第 1 条是真正影响可用性的 bug** —— 用户按正常流程操作会永远卡在追问循环里。
纯靠读代码发现不了，因为每一步单独看都是对的。

## 七、性能

生产构建产物：

| 包 | 大小 | gzip |
|---|---|---|
| echarts | 1134 KB | 377 KB |
| antd | 1158 KB | 367 KB |
| 业务代码 | 124 KB | 41 KB |
| react | 40 KB | 14 KB |

echarts 和 antd 单独切块，不阻塞首屏。本地演示项目没做进一步优化；
若要上线建议按需引入 antd 组件（`babel-plugin-import`）能减掉约 40%。

## 八、目录结构

```
frontend/
├── src/
│   ├── api/
│   │   ├── client.ts       # axios 封装 + SSE 解析 + 409 歧义提取
│   │   └── types.ts        # 与后端 schema 严格对齐的类型
│   ├── pages/
│   │   ├── DashboardPage.tsx   # 看板
│   │   ├── RecordPage.tsx      # 记录（饮食/运动/体重 三标签）
│   │   └── ChatPage.tsx        # 对话
│   ├── App.tsx             # 布局 + 路由 + 后端连接状态
│   ├── main.tsx            # Provider 装配
│   └── styles.css
├── scripts/
│   ├── verify_ui.mjs       # 21 项真浏览器验收
│   └── debug_confirm.mjs   # 定位确认弹窗问题的临时脚本
└── vite.config.ts          # 含 /api 代理与 SSE 缓冲关闭
```

**类型对齐的坑**：我第一版 `types.ts` 是照着印象写的，
和后端真实返回差了 6 处（`tdee` vs `tdee_value`、`recommend` 被 `{items}` 包了一层、
体重用 `moving_avg` 而非 `ma7`、`SSE` 是 `{type, data}` 嵌套而非扁平…）。
**正确做法是逐个接口 curl 一遍抄真实返回**，不要凭 schema 文件名推断。
